# Workflow notes

> Moved verbatim from `CLAUDE.md` by #274 (2026-10-06). Read before committing, pushing, spawning or retiring tabs in this repo.

## Workflow — GitHub issues are the backlog
- **The owner does nothing; `needs-owner` is retired for this project (owner rule 2026-09-25, scope soluciones-panel, panorama, mamparas-web, aures and riftcombo, #237).** Tokens, env vars, production migrations and dashboard reads are done by the orchestrator or an agent it delegates to (playwright MCP on the logged-in profile, the CLIs); only a password, 2FA or captcha screen is handed to him, in the same window. Do not file items as `needs-owner`.
- Every task the user names becomes a GitHub issue. Create it immediately with `gh issue create`, don't batch them up.
- Labels: `de-clone`, `ui`, `bug`, `data`, `legal`, `infra`. Reuse them; only add a new label when none fits.
- An issue body states what is wrong, the measured evidence, the files involved, and its dependencies on other issues. No vague one-liners.
- Close issues from commit messages (`Closes #4`) so the backlog does not drift from the code. Qualifying it does NOT scope it: `Closes #23 for web/main.ts` still closed all of #23 on push, and its second half had to be reopened by hand. When a commit does part of an issue, write `Refs #23`.
- `tasks/todo.md` is scratch for the current session only. GitHub issues are the durable backlog.
- **NEVER STOP WORKING (user rule, 2026-09-13).** Finishing the assigned brief is not the end of the session. When a task is done, pick the next one and start it: the open issues are the backlog, and if the backlog is genuinely empty, measure something and open an issue from what the measurement says. A session that reports a result and waits is a stopped session. **And an OFFER to continue is a wait with better manners - it is the same stop.** Demonstrated within an hour of this rule being written: the session closed a turn with *"continuing with the next gaps unless you want me somewhere else"*, which reads as momentum and is a full stop, because the turn ended and nothing happened until the user pushed. If the next task is known, the turn ends with it DONE or IN PROGRESS, never with it proposed. Ask only when proceeding would be unsafe or would waste the work if the answer went the other way. This is why the fleet went quiet overnight on 2026-09-12/13 - every lane finished its brief, went to `done`, and nothing restarted it, because no lane in this project self-dispatches and the manager is the only thing that hands out work.
- **A MANAGER SPAWNS LANES; IT DOES NOT SERIALISE THEM (user correction, 2026-09-13).** *"why didnt u create a new session tab to continue working"* - asked after a manager session closed the whole fleet, then worked four independent veins one after another in its own tab for hours. The global rule already says to parallelise implicitly, **without waiting to be asked**, and a manager doing lane work itself is the same stop as reporting and waiting: the queue drains at one lane's speed while three sit idle. **When two units of work do not depend on each other, they are two tabs**, spawned in the same breath with `mspawn --name <n> --prompt-file <f>`, and the manager keeps only what cannot be delegated. **The constraint that makes it safe is DISJOINT PATHS, not fewer lanes**: the tree and the index are shared, so each brief names the files that lane owns, and the contended files - `CLAUDE.md`, `data/combos.json`, `data/synergies.json` - stay with the manager while lanes report findings for him to apply. A lane that must touch a contended file STAGES instead (`.scratch-<lane>/staged.json`). Verify on agent ATTACH, never on status: `maestro list <id> --full` until `.agent.kind == "claude"`, then check `.agent.configHome` is `~/.personal-claude` - a maestro-SPAWNED agent gets an isolated config home and would never load this file.
- **CLOSE TABS WHEN THEY ARE NOT NEEDED (user rule, 2026-09-13).** A finished or idle tab is archived, not left on the shelf: `maestro archive <id> --force` (there is no `maestro close`; `maestro unarchive <id>` brings one back). Archive it once its work is committed and its findings are in a walk document or an issue - those are the durable records, and a tab id stops meaning anything the moment the session behind it is spent. 126 archived RiftCombo tabs had accumulated by 2026-09-13 and four more were sitting stopped; the shelf is not a log.
- **Several sessions share ONE working tree AND ONE INDEX, so commits are made with `git commit --only <paths>`, never from the staging area.** On 2026-09-06 a walk session ran `git add data/combos.json docs/phase0/walks/<file>` — path-scoped, as it should — and its `git commit` still swept four files another session had STAGED but not committed (src/combos.ts, src/matcher.ts and their tests), because `git commit` takes everything in the shared index. `git add <paths>` does not prevent that; `git commit --only <paths> -F -` (or `git commit -o <paths>`) does, because it commits exactly those paths whatever the index holds. Each session owns named paths (a walk: `data/combos.json` + `docs/phase0/walks/`; UI: `web/`, `src/`, `test/`; synergies: `data/synergies.json` + its test) and commits only those with `--only`; a NEW file needs `git add -N <path>` (intent-to-add) before `git commit --only <path>` accepts it, because `--only` cannot take an untracked path (rc-qa5, 2026-09-06); never stash or reset someone else's changes; before pushing, `git fetch` and push only when `origin/master` is an ancestor of `HEAD`.
- **A LANE'S `.scratch` DIRECTORY BELONGS TO ITS AUTHOR EXACTLY AS A SOURCE FILE DOES, AND RUNNING ITS SCRIPT AGAINST A FILE YOU OWN IS HOW YOU DAMAGE THE FILE (manager, 2026-09-13).** A lane built an emphasis repair for `data/combos.json` with proofs, offered to run it, and the manager ran it instead to save a round trip. **THE ROUND TRIP WAS THE SAFETY.** Three runs minutes apart returned **298 spans, then 326, then a corrected dry run of 28** — the author was editing the script between them, so each run caught a different intermediate state, and the 298-span write recased roughly 270 SENTENCE-INITIAL SPLICES THAT WERE CORRECT AS WRITTEN. A repair that damages what it touches, which this file already ranks as worse than one that hides. Reverted from a backup taken before the run and verified byte-identical. **The fix is not "read the script first" — it was read, and its abort conditions were real and held. The fix is that a script under active edit has no stable identity, so the only safe runner is the person editing it.**
- **IN THIS TREE A FAILED COMMIT IS USUALLY `.git/index.lock` AND IS NEVER A REASON TO FORCE OR TO DELETE THE LOCK (rc-kw and manager, 2026-09-13).** Six sessions share one index, so two commits landing in the same second collide. **Deleting a lock under a live `git` process is how an index gets corrupted**; retry on a short backoff and it lands on the first clear attempt. **AND WATCH THE SHELL CHAIN, because the failure is silent in the worst way**: `git commit … && git push …` with the commit failing on the lock still runs the rest of an `&&`-joined line if you wrote it as separate statements, and `git push` then answers *"Everything up-to-date"* — so a chain ending in `echo PUSHED` prints PUSHED for a commit that never happened. Verify a push by re-fetching and testing `git merge-base --is-ancestor <YOUR OWN COMMIT SHA> origin/work` — **never by the push command's own message, and NEVER BY `HEAD`**, because `HEAD` is shared and moves. A lane pushed successfully, fetched, tested `HEAD` and got NOT PUSHED, because another session had committed in the same tree between its push and its verify. **Capture your sha with `git rev-parse --short HEAD` immediately after your own commit and verify THAT.** **AND THE SAME REMEDY COVERS THE OPPOSITE FAILURE, MEASURED 2026-09-13: A REJECTED PUSH IS NOT A FAILED PUSH.** A lane's push was refused with `cannot lock ref refs/heads/work: is at d8b770a but expected a6ac7ac` **while its commit was already on the remote**, because another session in the shared tree had pushed it first. So on this branch a rejected push may mean you are done and a successful push may mean nothing happened — **both directions are answered only by `git merge-base --is-ancestor <YOUR OWN SHA> origin/work`, never by either command's message and never by `HEAD`.** **AND A RED SUITE IN A FILE YOU DO NOT OWN IS NOT EVIDENCE OF A COMMITTED DEFECT, WHICH COST A LANE AN ESCALATION AND A MANAGER THREE WORKTREE RUNS (2026-09-13).** `test/turn-clock.test.ts` failed on the shared tree with an ASSERTION rather than a timeout — `expected 5 to be 4` — and it passes at **every committed state**: 7 of 7 at `a078d06`, at `fbaf355` and at `978e027`, with 628 of 628 green at the sha then promoted, each run in a throwaway worktree checked out at that exact sha. **It was never red in any committed state.** The cause is the general one and it is worth more than the incident: **a coherent change that spans two files is INCOHERENT AT EVERY INSTANT BETWEEN THE TWO WRITES**, and here the two were `scripts/adversarial-check.mjs`, carrying a new clock model, and `test/turn-clock.test.ts`, carrying its pin — so another lane's full-suite run landed in the window and saw the new expectation against the old model. **This is the mirror of the in-flight-script damage recorded above: one ran a lane's script, the other ran the suite against a lane's half-written pair, and the single root cause is that A SHARED TREE HAS NO STABLE IDENTITY MID-EDIT** — which is exactly why the promotion procedure pins a sha and never a moving ref. **Re-run at a committed sha in a throwaway worktree before anyone acts; it takes under a minute and it is the same instrument as the promotion gate.** The lane was right twice over: it refused to touch a file it did not own, and it refused to choose between updating the pin and reverting the entry — the first would have hidden a live model change and the second would have undone a correct one.
