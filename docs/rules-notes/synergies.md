# Synergy notes

> Moved verbatim from `CLAUDE.md` by #274 (2026-10-06). Read before editing `data/synergies.json` or a synergy predicate.

## Synergies (#22)
- `data/synergies.json` is a SEPARATE file and must stay separate. `combos.json`'s whole value is that every row in it was walked by hand; a text-matched row in there destroys that invariant.
- The unit is a PATTERN: one `anchor` base code plus a `partner` predicate over the pool. The rule is hand-verified once and carries `basis.rules` (Core Rules paragraphs), optional `basis.readings` (R-numbers from issue #11) and `basis.combos` (the verified entries it was extracted from). The instances are text matches. **Regla verificada, instancias por texto** — the UI says so in its own words and never presents a pair as a combo.
- **Print the whole match list and read it before shipping a rule.** `npm run synergies` prints every list, `-- --match` prints only the fragment each predicate caught, `-- <id>` narrows. A rule whose list you cannot read end to end is written too loosely; `test/synergies.test.ts` caps a rule at 150 matches for that reason.
- What the predicates are allowed to lean on: 383.4.c.1 and 383.4.d.1 give `"When I conquer…"` / `"When I hold…"` as the standard wording of those trigger categories, and 823.1.b makes [Hunt] both. That is why the hold and conquer predicates are honest rather than guesses.
- False positives found by reading the lists, and the shapes they come in — check any new rule against all four: a **nested quote** (Relentless Pursuit and Zed, From the Shadows carry a trigger written for another permanent inside their own text); a **second trigger that is a no-op** (Blitzcrank returns himself to hand, Hallowed Tomb needs an empty Champion Zone) - **and note the scope, because a 2026-09-07 walk read it as a defect and it is not**: that exclude is right ON A MULTIPLIER RULE, where the second instance finds him already in hand. The same trigger is a REBUY on its own, since 315.2.b.2 Holds and 469.1 / 471.1 gain the point BEFORE it sends him back, so he is replayed each turn to drag another enemy body. An exclude is scoped to its rule; check which before calling it wrong; a **doubled drawback** (Vaults of Helia, Sigil of the Storm); and a **condition that cannot be met on the other event** — 383.4.g.1 says an ability whose non-conquer parts are unfulfilled never reaches the chain, which is what kills Tryndamere, Sivir, Yeti Brawler, Yone and Swain under Reckoner's Arena. Record each as an `excludes` entry with its reason; never drop one silently.
- Tokens and the two helper cards are filtered out of every list (`domains.length === 0 && !type.includes("battlefield")`), since a decklist can never hold one. An anchor banned in every format fails validation — that is how `stealthy-pursuer-move-triggers` was caught.
- **A keyword lens opens with `grep -i <word>`, never with `[Keyword]`.** The bracketed form misses
  every card that writes the mechanic in prose: 8 cards say `empower`/`disempower` in lower case with
  no brackets and 4 of those are legends, so a `\[Empower\]` sweep silently skipped the legends of
  the family it was hunting (#34, 2026-09-05). Open wide with `-i`, then close by reading the list.
- **A battlefield you provide starts UNCONTROLLED, so its text is off until you take it.** 190.1:
  *"Control is established over Battlefields through the course of play."* 190.6.d closes it: *"If the
  battlefield has no Controller, 'you' refers to no one, and all such instructions are ignored."* The
  project had cited 190.6.d for R8 but never its second sentence. So a `While you control this
  battlefield` discount is NOT a deckbuilding freebie — walking a body there and establishing Control
  (466.5) is part of the entry's cost. Six battlefields print that wording; only SFD-211 Marai Spire
  is in the catalogue, and `ezreal-marai-spire-free-repeat` says so in its own notable (2026-09-05).
- **A battlefield is drawn at random, and only in some formats, and you cannot stack copies of it.** 485.4.a: a
  player provides three and only 1 is used; **485.5 and 487.5 say "randomly selects"**, while **486.5 says only
  "selects"**. So two of your battlefields never share a board (#33 fixes the synergy layer on this), and a
  battlefield-dependent combo is not certain to come online. **AND THE STANDING CAVEAT — glossed on 81 entries as "one in three, at random" — IS WRONG IN BOTH DIRECTIONS FOR A MATCH, because nobody read 486.5 to the end (corrected 2026-09-12, #187 batch 32).** Its second half: *"After this game, if a player won, the Battlefields that were used are to be removed and not selected again for this Match. One of the remaining Battlefields that were set aside must be chosen instead"*, with 486.6 spelling out the wrapper (best of 3; after a game win, reset, remove the battlefields in play, choose new ones from those set aside). **So in a DUEL (485) it is one in three AT RANDOM; in a MATCH (486) it is a FREE CHOICE IN GAME 1 and then REMOVED for the rest of the match.** Both halves matter: game 1 has no randomness at all, so a line needing `OGN-293 The Grand Plaza` or `SFD-214 Power Nexus` has it **whenever it wants** — strictly BETTER than the caveat says — while games 2 and 3 cannot repeat it, so the line executes in **at most one game of three** — strictly WORSE than "one in three at random", because random draws are independent and this is a REMOVAL. 486.5.a looked like the only relief (*"If no player won a game, the battlefields presented for that game may be reused"*) — **and for a COMPETITION that is overruled: TOURNAMENT RULES 406.1.b reads *"If a game ends in a draw, players must use the same battlefields for the following game"*, and TR 104.1 gives the contradiction to this book. A drawn game LOCKS the battlefield rather than returning it as an option** (corrected 2026-09-12), 103.4.c is why the obvious dodge fails, and 486.6.a allows a removed battlefield back only in games 4-5 of a best-of-5, after each of yours has been presented once and never more than twice. **Reassuringly, no arithmetic moves**: 486.3 is Victory Score 8 and 486.4 is Battlefield Count 2, so a Match GAME is a Duel in every parameter except the rotation, and 486.7 is word-for-word 485.7, so the turn-clock model needs no adjustment. Bringing 3 copies of the same battlefield is NOT a
  way out: **Core Rules 103.4.c** ("Cannot include more than one of a Battlefield of the same name when there
  are more than one required for the deck") and **Tournament Rules 402.1** ("exactly 3 battlefields each with a
  unique name") both forbid it. Issue #35 (2026-09-05) was opened believing the Core Rules were silent on this;
  they are not — 103.2.b is the Main Deck cap, the battlefield cap is three paragraphs further down. Every entry
  that needs a specific battlefield states this in `prerequisites.notable`, per format.
- **`basis.combos` means "the verified entries this rule was extracted from", which is NOT the same as "entries whose `uses[]` contain the anchor" — and the file holds both kinds.** Measured 2026-09-07 over 386 references: 27 point at an entry that does not run the anchor card, because the entry demonstrates the same MECHANISM with a different payoff (`tryndamere-excess-damage-might-reduction` -> `sivir-ambitious-frigid-touch-excess`, `dauntless-vanguard-occupied-battlefield-assault` -> `stare-down-arachnoid-horror-lone-survivor`). Both readings are legitimate and neither is a defect; what is a defect is a batch claiming it verified the anchor is present when two of its 77 new references are of the other kind. State which kind you are adding, and do not "fix" the existing ones.
- A rule that matches most of the pool is a fact about the pool, not a pairing. "Retreat replays any play effect" measured 132 and was narrowed to play effects that leave another permanent behind (14).
- UI lives in the deck panel **below** "What to add", so #18 keeps the placement the user chose.
