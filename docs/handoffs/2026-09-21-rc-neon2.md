# rc-neon2 handoff — 2026-09-21

Sub-project C, **phase one only**: measure, decide, amend the spec, write the plan. **No cutover was
performed.** `web/supabase.ts` is untouched, no Supabase project was touched, nothing was deployed,
and the Neon project's `main` branch was read from and never written to.

## 1. The thing to know first: the credential is NOT an environment variable

There is **no `NEON_*` variable in the environment** — `env | grep -i neon` is empty — and the brief
anticipated that being the first blocker. **It is not one.** `neonctl` on this machine is **already
authenticated**: `neonctl projects list` prompts for an organisation rather than for a login.

**`neonctl api <path>` is an authenticated passthrough to the Management API**, so every measurement
in this session was taken **without a secret ever entering a transcript**. That is a better posture
than holding a key and it should be kept.

A second thing worth recording, because the brief asked for it and it could not be done: **a Bash
hook in this profile refuses any command whose text contains `.env`**, so `ls -la .env.local` is
denied even though the profile's `deny` list only names the `Read`/`Edit` tools. I did not work
around it — the file exists (visible via `ls -a`) and its variable names were never read. It did not
matter, because `neonctl` made the question moot.

## 3. The fork is decided: **the SQL function, not Route C**

Spec §5.3 selected Route C — an Edge function calling the Management API with a deployed
`NEON_API_KEY`. **That is superseded.** The worktree's `neon/migrations/0002_delete_account.sql` is
the route to build: a `SECURITY DEFINER` function, no parameter, no endpoint, **no deployed secret**.

The decisive measurement is one line: **`set role authenticated; select public.delete_account();`
SUCCEEDS**, while `authenticated` holds neither `USAGE` on schema `neon_auth` nor `DELETE` on
`neon_auth."user"`. The `SECURITY DEFINER` escalation works through the Data API's own role — the one
thing that was genuinely unknown. `anonymous` is refused outright. The cascade was then measured end
to end on a throwaway branch: 1/1/1 → **0/0/0** for the victim, the other user untouched, **zero
orphans**.

**Why §5.3 chose otherwise is worth knowing rather than dismissing:** it preferred C because C's
completeness had been *measured* and A's had not. A's is measured now, it is the **same cascade**,
and every other axis — secret, attack surface, "what aims the delete", worst possible bug, distance
from today's code — favours A. §5.3's own sentence, *"that is a third reason to prefer Design A"*,
was right and was overruled by an evidence asymmetry that no longer exists.

**Consequences:** `api/delete-account.ts` is **not built**, `@neondatabase/serverless` is **not**
added, no `NEON_API_KEY` is deployed, and §7.3's widening of the secret-name check shrinks to the
connection string alone.

## 4. Two findings that are in neither the spec nor the branch, and each would have cost a session

**(a) `authenticated` has `EXECUTE` on `auth.uid()` and NO `USAGE` on schema `auth`.** A direct
`select auth.uid()` as that role answers *permission denied for schema auth*, while the RLS policies
that call it work fine — schema `USAGE` is a **name-resolution** check and a stored policy expression
already holds the function's OID. **This lands on check 16 of `scripts/check-rls-neon.mjs`**: do not
implement it as a read of `auth.uid()`, it fails with an error that reads exactly like a denial.
panel3's version — insert without `user_id`, let the default fill it, compare to the token's `sub` —
is immune, and this is a second, independent reason to keep it.

**(b) A signed-out visitor is refused at the GRANT, not filtered by RLS.** `anonymous` holds no
privilege on `public.decks` at all → *permission denied for table decks*. That is stronger than
filtering to zero rows, and it confirms commit `e458b70`. It does **not** contradict §4's seventh
vacuity instance (the Data API refusing a credential-less request at the door with `400`) — **two
layers, both true** — and check 9 must still pair its refusal with a positive control on the same URL.

## 7. Traps paid for in this session

- **`neonctl psql` refuses a branch with several roles** — *"Multiple roles found … authenticator,
  anonymous, authenticated, neondb_owner"*. Pass `--role-name neondb_owner`. That error message is
  also the cheapest way to enumerate the Data API roles.
- **`neonctl endpoints list` does not exist.** Use `neonctl api /projects/<id>/endpoints`.
- **`neonctl projects list` with no `--org-id` opens an interactive picker** and hangs a
  non-interactive shell. Always pass the org.
- **A compound Bash command containing `.env` is refused even when every part of it is harmless** —
  the hook matches the text of the command, the same class as the `pkill -f` trap this project
  records.
- **`select ... pg_get_function_identity_arguments(oid) ... from pg_proc p join pg_namespace n`**
  fails with *column reference "oid" is ambiguous*. Qualify it `p.oid`.
- **The first thing `neonctl neon-auth status` says is alarming and is not a problem**: *"Neon Auth
  is not configured for this branch"* while the schema, the rows and all five FKs are intact. **I
  nearly reported that as a blocker.** It is the finding for open item 1, not a fault.

## 8. What was NOT done, and why

- **No cutover.** The brief scoped this to phase one.
- **The `/rpc/delete_account` call through PostgREST with a real JWT was not made**, because Neon
  Auth is not enabled and there is no way to mint a real token without O1. It is step 3 of the plan
  and it is the last thing standing between §12.6's decision and proof.
- **`neon-auth disable` was not run against `main`.** It was run against the throwaway branch, where
  it answered *"integration not found"*. Disabling on `main` is not a thing this session was asked to
  do and it is not reversible without O1.
